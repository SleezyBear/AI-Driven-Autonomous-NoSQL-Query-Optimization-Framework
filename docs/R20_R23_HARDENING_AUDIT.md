## R22 — PostgreSQL operations

The centralized SQLAlchemy/asyncpg engine uses pre-ping, a pool of 5 with 5
overflow connections, a 30-second pool wait, 1,800-second recycle, 10-second
connect timeout, 60-second statement timeout, and 5-second lock timeout by
default. Values are bounded and configurable.

Connection capacity is calculated per process:

```text
connections_per_process = POSTGRES_POOL_SIZE + POSTGRES_MAX_OVERFLOW
deployment_budget = (api_processes + worker_processes) * connections_per_process
```

With defaults, each API or worker can consume at most 10 connections; two API
and two worker processes therefore budget 40. Operators must keep that total,
migration sessions, and an administration reserve below PostgreSQL
`max_connections`. Pool bounds are per process, not per deployment.

The migration environment acquires a PostgreSQL session advisory lock with a
bounded wait before Alembic owns its transaction. Migration `0019` adds seven
operational indexes for pending/expired job claims, requester/target run lists,
approval expiry, production-ledger reads, and run audit/artifact reads. Its
downgrade deliberately fails pending an approved maintenance plan.

Disposable acceptance proved:

- fresh database to head and representative `0018` to current head;
- two concurrent migration runners serialized safely;
- `pg_dump -Fc` followed by `pg_restore` into a different fresh database;
- restored run/job identity plus snapshot, diagnosis, candidate, approval,
  deployment, monitoring outcome, and rollback evidence; immutable snapshot and
  candidate fingerprints; five representative operational indexes; and a valid
  production-ledger hash chain;
- a forced PostgreSQL pause produced an outage, unpause restored service, and
  durable job state remained unchanged;
- server capacity was readable and usable after recovery.

Repository transaction scopes were audited against the long-running pipeline
boundaries. PostgreSQL transactions remain scoped to repository mutations and
do not enclose Ollama inference, benchmark execution, Mongo mutation,
monitoring waits, or human approval waits.

## R23 — MongoDB operations

All production sync/async construction uses the Mongo connection layer. Default
bounds are 5-second server selection/connect, 30-second socket, pool 0–20,
10-second wait queue, and 60-second idle lifetime. Reads/writes use the driver's
topology-aware retry behavior, clients are process-reused by their owning
components, and owners close clients on exit.

Production rejects development credentials and `directConnection=true`, enables
TLS with certificate and hostname verification, and accepts explicit CA/client
certificate paths only when readable. URI rendering strips user info and
redacts sensitive query parameters. The read-only probe discovers hello/build
version, standalone/replica-set/sharded topology, primary state, FCV, and MongoDB
8 query-settings capability without application data mutation.

Disposable acceptance proved:

- trusted-CA TLS succeeds while a separately generated untrusted CA fails;
- an isolated executor can read and create/drop its exact owned index but cannot
  insert documents, drop a collection/database, or set server parameters;
- a replica-set client discovers topology and primary state, then recovers after
  forced primary stepdown and re-election;
- a complete Mongo outage is observed, restart recovers, and the durable
  reconciliation marker remains at exactly one mutation.

The failover drill uses a disposable single-member replica set to exercise
driver topology discovery and election recovery. Multi-member failover under
network partition, long soak/load behavior, and broader adversarial qualification
remain explicit R24–R27 residual work; no weaker TLS, consistency, durability,
or deployment authority was introduced.
